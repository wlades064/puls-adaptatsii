# Проверка процесса адаптации

## Локальный прогон

Запустите приложение по README. Импортируйте вымышленную задачу о приёме и повторите ту же команду. В кабинете HR должна появиться одна карточка с одной ссылкой. Проверьте ещё два вымышленных сценария через обычное добавление сотрудников.

| Сценарий | Ожидаемый результат |
|---|---|
| Склад. У сотрудника нет доступа к системе учёта | HR получает обращение, назначает исполнителя, тот фиксирует, что доступ выдан и проверен. |
| Магазин. Сотрудник ответил «Да» на все вопросы | Ответ виден в карточке сотрудника. Очередь обращений не меняется. |
| Офис. Сотрудник просит связаться с HR и отмечает вопрос о руководителе | Обращение получает HR. Другому ответственному оно недоступно. |

## Что измерять на пилоте

- Время до первого действия: от создания обращения до первого назначения, включая назначение на HR. Для обращений без назначения запишите текущий возраст отдельно. Время измеряет реакцию в приложении, а не момент фактического контакта с сотрудником.
- Закрытие с результатом: число обращений, закрытых с описанием результата, из всех обращений за период. Отдельно отметьте случаи, в которых устранение проблемы подтверждено сотрудником. Статус «Закрыто» сам по себе этого не подтверждает.
- Заполняемость: число полученных ответов из числа реально переданных ссылок. Передачу ссылок HR отмечает вручную, поскольку приложение учитывает создание ссылки.

Для короткого пилота можно начать с одного подразделения и опроса в первую неделю. До старта согласуйте с HR срок реакции, кто обрабатывает чувствительные обращения и как фиксировать подтверждение результата. Бизнес-эффект на текучесть потребует наблюдения за когортой в течение 90 дней.

## Что проверить на портале ТГТ

1. Получить у HR обезличенный пример задачи о приёме и подтвердить устойчивый признак. Например, отдельное пользовательское поле с фиксированным значением. Уточнить, заполнены ли обязательные поля при создании. Если они появляются позже, согласовать запуск после заполнения.
2. Попросить администратора проверить, что тариф поддерживает REST, а учётная запись интеграции имеет область `task` и доступ только к нужным задачам. На тестовой задаче проверить наличие согласованного признака и полей в `tasks.task.get`. Пользовательские поля нужно явно запросить в `select`. [Чтение задачи и права](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-get.html), [вебхуки](https://apidocs.bitrix24.com/local-integrations/local-webhooks.html)
3. Если поля готовы при создании, проверить доставку `ONTASKADD`, подлинность события и соответствие ID прочитанной задачи. Событие сообщает о создании задачи и передаёт её ID. Для нескольких порталов потребуется ключ из ID портала и ID задачи. [Событие создания задачи](https://apidocs.bitrix24.com/api-reference/tasks/events-tasks/on-task-add.html)
4. Если нужны поручения в Битрикс24, на тестовой задаче проверить права создания и видимость. Передавать краткое поручение HR с ID обращения. Исходные ответы и комментарии остаются в «Пульсе адаптации». [Создание задачи](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-add.html)
